# Telegram-бот для заучивания английских слов (Oxford 3000)

Личный многопользовательский бот на `aiogram 3`: присылает слова из словаря
Oxford 3000 по расписанию в вашем часовом поясе, показывает перевод (спойлером
или по кнопке), определение, пример, коллокации, синонимы и антонимы, а ответы
**«Знаю» / «Не знаю»** двигают слово по системе интервального повторения (SRS).

Данные хранятся в локальном SQLite-файле — ни Docker, ни облако не нужны.

## Возможности

- **Регистрация через `/start`**: выбор часового пояса (IANA, с проверкой через
  `zoneinfo`), количества слов в день (1–50) и временного окна рассылки.
- **Рассылка по слотам**: окно делится на `words_per_day` равных интервалов,
  каждое сообщение приходит в своём слоте в местном времени пользователя.
- **Порядок очереди**: сначала повторения, которых сегодня ещё не было (самые
  просроченные вперёд), затем новое слово, и только если других вариантов не
  осталось — слово, которое сегодня уже показывали (этап 0 = «в очередь на
  сегодня»), поэтому `/word` не зацикливается на одном слове.
- **Два режима показа**: «сначала слово, потом перевод» (по умолчанию, кнопка
  **Показать**) и «всё сразу» (перевод под спойлером `||...||`).
- **Озвучка слов**: две кнопки **🔊 🇬🇧 UK** и **🔊 🇺🇸 US** рядом с ответами
  присылают mp3 слова отдельным сообщением — из `data/uk` (британский) и
  `data/us` (американский), см. [озвучку](#озвучка-слов).
- **Настраиваемая карточка**: какие поля показывать (Definition, Example,
  Part of Speech, Related Forms, Synonyms, Antonyms, Collocations) и фильтр по
  части речи (`noun` / `verb` / `adjective` / `adverb` / `other` / все).
- **SRS по таблице этапов** 0 → 1 → 3 → 7 → 14 → 30 → 90 дней: «Знаю» поднимает
  этап, «Не знаю» сбрасывает на нулевой, выученные слова возвращаются на
  освежение раз в 90 дней и **не расходуют дневной лимит**.
- **Лимит слов в изучении** (по умолчанию 100, меняется в `/settings`, `0` — «без
  ограничения»): пока слов «в изучении» не меньше лимита, новые слова не
  показываются — ни по расписанию, ни по кнопке «🎲 Слово». Повторения уже
  начатых слов и освежение продолжают приходить.
- **Случайные новые слова**: очередное новое слово выбирается не по порядку
  загрузки словаря, а случайно (`ORDER BY random()`), приоритет — у слов, которых
  у пользователя ещё не было.
- **Пауза и возобновление** (`/pause`, `/resume`), слово вне расписания
  (`/word`), статистика (`/stats`).
- **Перезапуск не теряет данные**: расписания активных пользователей
  восстанавливаются из БД при старте.
- **Устойчивость**: ошибки одного апдейта не «роняют» бота, недоступный
  пользователь (заблокировал бота) ставится на паузу автоматически.
- **Логи** в консоль и файл (`loguru`).

## Требования

- Python 3.11+
- Токен бота от [@BotFather](https://t.me/BotFather)
- Windows или Linux (вручную; автозапуск — Планировщик заданий Windows или
  `systemd` на Linux, см. [развёртывание](#развёртывание-на-сервере-linux-systemd))

Зависимости (`requirements.txt`): `aiogram`, `aiosqlite`, `SQLAlchemy[asyncio]`,
`APScheduler`, `pydantic-settings`, `loguru`; для тестов — `pytest`,
`pytest-asyncio`.

## Быстрый старт

```powershell
# 1. Перейти в каталог проекта
cd c:\project\tele_eng

# 2. Создать и активировать виртуальное окружение
python -m venv .venv
.\.venv\Scripts\Activate.ps1        # Windows (PowerShell)
# source .venv/bin/activate         # Linux / macOS

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Создать .env из шаблона и вписать токен
Copy-Item .env.example .env

# 5. Запустить бота
python main.py
```

При первом запуске бот создаст файл базы (`bot.db`), схему таблиц и
автоматически импортирует словарь из `data/…csv`, если таблица `words` пуста.
Затем в логах появится `Бот запущен, начинаю опрос Telegram`.

Остановка — `Ctrl+C`.

### Запуск без активации venv

```powershell
.\.venv\Scripts\python.exe main.py
```

### Запуск в фоне (Планировщик заданий, Windows)

`run_bot.cmd` запускает бота с дублированием вывода в `logs\console_out.txt` и
`logs\console_err.txt`. Задача Планировщика живёт независимо от терминала, бот
не останавливается после закрытия окна:

```powershell
schtasks /create /f /tn tele_eng_bot /tr '"C:\Windows\System32\cmd.exe" /c "C:\project\tele_eng\run_bot.cmd"' /sc once /st 23:59
schtasks /run /tn tele_eng_bot      # запустить
schtasks /query /tn tele_eng_bot    # состояние
schtasks /end /tn tele_eng_bot      # остановить
```

`run_bot_bg.cmd` делает то же самое через `pythonw.exe`: консольное окно не
создаётся вообще, поэтому запуск не привязан ни к какому терминалу. Скрипт
защищён от второго экземпляра — если бот уже работает, он ничего не делает. Его
удобно повесить в Планировщик как «сторожа» (перезапуск после падения):

```powershell
schtasks /create /f /tn tele_eng_bot_bg /tr "C:\project\tele_eng\run_bot_bg.cmd" /sc minute /mo 5
```

Запускайте **только один** экземпляр бота: второй процесс с тем же токеном
начинает отбирать `getUpdates`, в логах появляется `TelegramConflictError`, и бот
перестаёт отвечать на команды (а кнопки в старых сообщениях, если у экземпляров
разные базы, — «⚠️ Не нашёл это слово в истории отправок»).

### Остановить локального бота

Если бот переехал на сервер, локальный экземпляр нужно выключить вместе с задачей
Планировщика: иначе задача поднимет его снова, и оба процесса начнут делить
`getUpdates`.

```powershell
Get-ScheduledTask | Where-Object { $_.Actions.Arguments -match 'tele_eng' } |
    Select-Object TaskName, State                                    # имя задачи

Stop-ScheduledTask    -TaskName tele_eng_bot
Disable-ScheduledTask -TaskName tele_eng_bot                         # не перезапустится

Get-CimInstance Win32_Process -Filter "Name like 'python%'" |
    Where-Object { $_.CommandLine -match 'main\.py' } |
    ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

Проверка, что апдейты свободны: запрос
`https://api.telegram.org/bot<TOKEN>/getUpdates` возвращает обычный JSON
(`"ok":true`) — значит polling никто не держит; `409 Conflict` — кто-то ещё
работает (в том числе серверный `systemd`).

Вернуть бота на ноутбук (и не забыть остановить серверный:
`sudo systemctl stop tele-eng-bot`):

```powershell
Enable-ScheduledTask -TaskName tele_eng_bot
Start-ScheduledTask  -TaskName tele_eng_bot
```

### Развёртывание на сервере (Linux, systemd)

Бот работает через long polling: домен, SSL-сертификат и открытые порты не нужны —
достаточно исходящего доступа в интернет. На VPS (Ubuntu 22.04+ / Debian 12+) он
ставится как сервис `systemd`, база и `.env` лежат рядом с проектом, поэтому Docker
не требуется. Хватает 1 vCPU / 512 МБ RAM / 1 ГБ диска.

```bash
# 1. Пакеты и код (приватный репозиторий — по токену или SSH-ключу сервера)
sudo apt update && sudo apt install -y git python3 python3-venv
sudo git clone https://github.com/KViachaslav/tele-eng-bot.git /opt/tele_eng
sudo chown -R "$USER":"$USER" /opt/tele_eng

# 2. Установка: пользователь teleeng, .venv, зависимости, .env, юнит systemd
cd /opt/tele_eng
sudo bash deploy/install.sh

# 3. Токен: пока в .env нет реального BOT_TOKEN, сервис не запускается
sudo nano /opt/tele_eng/.env          # BOT_TOKEN=<токен от @BotFather>
sudo systemctl start tele-eng-bot
```

`deploy/install.sh` создаёт системного пользователя (`teleeng`), отдаёт ему каталог
проекта, ставит зависимости из `requirements.txt`, готовит `.env` из шаблона,
подставляет реальные пути в `deploy/tele-eng-bot.service` и включает автозапуск.
Имена переопределяются переменными окружения:
`sudo RUN_USER=mybot SERVICE_NAME=mybot bash deploy/install.sh`.

#### Проверка состояния и логи

```bash
systemctl status tele-eng-bot          # активен ли сервис
journalctl -u tele-eng-bot -f          # живой поток логов
journalctl -u tele-eng-bot -n 100      # последние 100 строк
tail -f /opt/tele_eng/logs/bot.log     # файл логов (LOG_FILE в .env)
```

При падении сервис поднимается через 10 секунд (`Restart=always`, `RestartSec=10`),
после перезагрузки сервера стартует сам (`systemctl enable`). Расписания
пользователей восстанавливаются из базы при старте
(`SchedulerService.restore_all`), поэтому перезапуск не сбивает рассылку, а
пропущенные во время простоя слоты «задним числом» не догоняются
(`misfire_grace_time`).

#### Ручная установка юнита (если не используете `deploy/install.sh`)

```bash
sudo useradd --system --home-dir /opt/tele_eng --shell /usr/sbin/nologin teleeng
sudo chown -R teleeng:teleeng /opt/tele_eng
sudo install -d -o teleeng -g teleeng /opt/tele_eng/logs
sudo -u teleeng python3 -m venv /opt/tele_eng/.venv
sudo -u teleeng /opt/tele_eng/.venv/bin/pip install -r /opt/tele_eng/requirements.txt

sudo sed -e 's|@PROJECT_DIR@|/opt/tele_eng|g' -e 's|@RUN_USER@|teleeng|g' \
    /opt/tele_eng/deploy/tele-eng-bot.service \
    | sudo tee /etc/systemd/system/tele-eng-bot.service > /dev/null
sudo systemctl daemon-reload
sudo systemctl enable --now tele-eng-bot
```

`.env` бот читает сам (`config.Settings`), а относительные `DB_PATH`, `CSV_PATH` и
`LOG_FILE` считаются от каталога проекта, поэтому `bot.db` и `logs/` можно
оставить рядом с кодом (каталогу `logs/` нужны права на запись для сервисного
пользователя). В юните обязаны быть подставлены реальные пути: строки
`@PROJECT_DIR@` / `@RUN_USER@` — это заготовки для `sed`, а не готовые значения.

#### Обновление версии на сервере

Остановить → забрать новый код → поставить зависимости → запустить:

```bash
cd /opt/tele_eng
sudo systemctl stop tele-eng-bot
sudo -u teleeng git pull
sudo -u teleeng .venv/bin/python -m pip install -r requirements.txt   # если менялись зависимости
sudo systemctl start tele-eng-bot

systemctl status tele-eng-bot --no-pager     # active (running)
journalctl -u tele-eng-bot -n 30             # ошибки старта, если что-то не так
```

Всё то же самое делает повторный запуск установщика: он идемпотентен — обновляет
зависимости, заново подставляет пути в юнит, перезагружает systemd и
перезапускает сервис:

```bash
cd /opt/tele_eng && sudo bash deploy/install.sh
```

`git pull` выполняется от сервисного пользователя (`teleeng`) — он владелец
каталога после установки. Если каталог принадлежит `root`, git откажется работать
(«detected dubious ownership»): верните владельца
`sudo chown -R teleeng:teleeng /opt/tele_eng`. Для приватного репозитория
используйте токен в URL или SSH-ключ сервера; `.env` и `bot.db` в git не входят и
при обновлении не затрагиваются.

Если бот переезжает с локальной машины на сервер, перенесите базу и настройки
(`bot.db`, файлы `bot.db-wal`/`bot.db-shm` и `.env`) — иначе на сервере стартует
свежая база, история SRS останется локально, а кнопки в старых сообщениях начнут
отвечать «⚠️ Не нашёл это слово в истории отправок».

Если в обновлении менялся `deploy/tele-eng-bot.service`, переустановите юнит:
systemd запускает файл из `/etc/systemd/system`, а не шаблон из репозитория.

```bash
cd /opt/tele_eng
sudo sed -e 's|@PROJECT_DIR@|/opt/tele_eng|g' -e 's|@RUN_USER@|teleeng|g' \
    deploy/tele-eng-bot.service | sudo tee /etc/systemd/system/tele-eng-bot.service > /dev/null
sudo systemctl daemon-reload
sudo systemctl restart tele-eng-bot
```

Новые настройки, если они появились, видно сравнением шаблона с рабочим файлом
(`diff .env .env.example`): незаданные переменные бот берёт из значений по
умолчанию в `config.py`, поэтому `.env` обычно можно не трогать.

Откат на предыдущую версию — по коммитам:

```bash
cd /opt/tele_eng
sudo -u teleeng git log --oneline -5          # что установлено сейчас
sudo systemctl stop tele-eng-bot
sudo -u teleeng git checkout <коммит>         # вернуться к рабочему коммиту
sudo -u teleeng .venv/bin/python -m pip install -r requirements.txt
sudo systemctl start tele-eng-bot
```

Схему базы бот обновляет сам при старте (`db/migrations.py`), отдельные миграции
запускать не нужно. Словарь из `data/*.csv` повторно не импортируется — импорт
идёт только если таблица `words` пуста. Остановка на пару секунд рассылку не
сбивает: расписания восстанавливаются из базы при старте
(`SchedulerService.restore_all`), а карточки, уже отправленные в чат, продолжают
работать — журнал отправок лежит в `bot.db`. Не запускайте рядом второй экземпляр
(`sudo -u teleeng python main.py`) и не поднимайте бота с тем же токеном локально —
два процесса с одним токеном дают `TelegramConflictError`.

#### Бэкап, перенос базы и удаление сервиса

База — один файл SQLite в режиме WAL, поэтому копируйте её либо при остановленном
сервисе, либо штатным средством SQLite:

```bash
sudo systemctl stop tele-eng-bot
sudo cp /opt/tele_eng/bot.db /root/bot-$(date +%F).db

# консистентная копия без остановки бота
sudo -u teleeng python3 -c "import sqlite3; sqlite3.connect('/opt/tele_eng/bot.db').execute(\"VACUUM INTO '/opt/tele_eng/backup.db'\")"
```

Переезд на другой сервер: скопируйте `bot.db` и `.env` в каталог нового проекта и
запустите сервис. **Остановите бота на старом сервере** — два процесса с одним
токеном дают `TelegramConflictError`.

```bash
sudo systemctl disable --now tele-eng-bot     # остановить и убрать из автозапуска
sudo rm /etc/systemd/system/tele-eng-bot.service
sudo systemctl daemon-reload
```

## Настройки `.env`

Файл `.env` лежит рядом с `main.py`. Все переменные описаны в `.env.example`:

| Переменная | Обязательна | По умолчанию | Назначение |
|------------|-------------|--------------|------------|
| `BOT_TOKEN` | да | — | Токен от @BotFather |
| `DB_PATH` | нет | `bot.db` | Путь к файлу SQLite (относительный — от корня проекта) |
| `CSV_PATH` | нет | `data/oxford3000_…csv` | Путь к словарю для автоимпорта |
| `LOG_LEVEL` | нет | `INFO` | `DEBUG` / `INFO` / `WARNING` / `ERROR` |
| `LOG_FILE` | нет | `logs/bot.log` | Файл логов (пусто — только консоль) |
| `DEFAULT_TIMEZONE` | нет | `Europe/Moscow` | Часовой пояс по умолчанию |

Без `BOT_TOKEN` бот не стартует: в логе появится сообщение об ошибке и код
возврата 1.

## Словарь и импорт CSV

Исходный файл:
`data/oxford3000_vocabulary_with_collocations_and_definitions_datasets.csv`
(≈3300 слов) с колонками `Word`, `Definition`, `Russian Translation`,
`Example Sentence`, `Part of Speech`, `Related Forms`, `Synonyms`, `Antonyms`,
`Collocations`.

- **Автоимпорт.** При запуске `python main.py` бот проверяет таблицу `words`:
  если она пуста — импортирует `CSV_PATH` (кодировка определяется
  автоматически: UTF-8, UTF-8-BOM, cp1251).
- **Ручной импорт** (дополнить или загрузить свой файл):

```powershell
# файл из CSV_PATH (.env)
python scripts/import_csv.py

# свой файл
python scripts/import_csv.py path\to\words.csv

# принудительно задать кодировку
python scripts/import_csv.py path\to\words.csv --encoding cp1251
```

Импорт **идемпотентен**: уникальный индекс по `word` не даёт создать дубликат,
повторный запуск просто пропускает уже загруженные слова. Фактический результат
для штатного файла (3354 строки, кодировка UTF-8 с BOM):

```
Импорт завершён: всего строк 3354, добавлено 3353, уже было 0, дублей в файле 0, без слова 1.
```

Повторный запуск выводит `добавлено 0, уже было 3353` — данные не дублируются.

Пустые ячейки сохраняются как `NULL` и в сообщении не показываются. Значения в
кавычках, запятые внутри значений и лишние пробелы обрабатываются корректно.

## Озвучка слов

Кнопки **🔊 🇬🇧 UK** и **🔊 🇺🇸 US** появляются в карточке рядом с «Знаю» /
«Не знаю» и присылают отдельным сообщением mp3 с произношением слова в выбранном
акценте: подпись «`apple — 🇬🇧 UK`», в тегах файла — слово и `Oxford 3000`.

```
data/uk/apple_uk.mp3     британское произношение
data/us/apple_us.mp3     американское произношение
```

- **Акцент выбирает пользователь.** Он лежит в `callback_data` кнопки
  (`audio:uk:12:34`), каталоги перечислены в `config.AUDIO_ACCENTS`
  (`("uk", "us")`) — это же порядок кнопок в карточке. Если файла в выбранном
  акценте нет, приходит алерт про этот акцент: молча подставлять другой акцент
  бот не будет.
- **Поиск файла.** Имя файла не обязано совпадать с написанием слова из базы
  регистр в регистр: каталог акцента один раз сканируется в индекс по ключу в
  нижнем регистре, при этом пробел, дефис, подчёркивание и апостроф считаются
  одним и тем же (`services/audio.py`). Поэтому находятся `Internet`, `TV`,
  `T-shirt` и словосочетания с пробелом в имени файла (`ice cream_uk.mp3`).
- **Коллизии регистра.** Windows не различает регистр, поэтому при распаковке
  архива `it_uk.mp3` и `IT_uk.mp3` превратились в `it_uk.mp3` и
  `IT_uk(1).mp3`. Если по ключу в каталоге нашлось несколько файлов, побеждает
  тот, чьё написание совпадает со словом из базы точь-в-точь: «it» получает
  `it_uk.mp3`, а «March» (месяц) — `March_uk(1).mp3`, а не файл глагола
  `march_uk.mp3`. Такие копии есть в обоих каталогах: `IT_uk(1).mp3`,
  `March_uk(1).mp3`, `May_uk(1).mp3` и то же самое с `_us`.
- **Фразовый глагол не путается со слитным словом.** «work out» и «workout» —
  разные статьи Oxford 3000, поэтому число слов в ключе должно совпадать и
  `workout_uk.mp3` по запросу «work out» не находится (как и `per cent_uk.mp3`
  по запросу «percent»).
- **Озвучен не весь словарь.** В Oxford 3000 есть словосочетания и формы, для
  которых mp3 в архиве нет (`account for`, `a.m.`, `Mrs`, а также фразовые
  глаголы `work out`, `break down`, `percent` и подобные — 417 слов из 3353,
  озвучено 2936). Для такого слова приходит алерт «🔇 … озвучки для этого слова
  нет», а карточка и ответы работают как обычно.
- Кнопки не влияют на SRS: прогресс меняют только «Знаю» / «Не знаю».

## Как работает рассылка

1. Окно `window_start … window_end` делится на `words_per_day` равных
   интервалов: `interval = (end - start) / words_per_day`.
   Пример: 10 слов с 09:00 до 21:00 → каждые 72 минуты.
2. Для каждого пользователя в планировщике живёт **одна** задача с датой
   следующего слова (`DateTrigger`). После каждой отправки следующий слот
   рассчитывается заново, поэтому смена окна, лимита, часового пояса и пауза
   вступают в силу сразу.
3. Время считается в часовом поясе пользователя (`zoneinfo`), в БД хранится
   UTC.
4. Если подходящих слов нет, слот остаётся пустым — ничего не отправляется.
   Новые слова не берутся и тогда, когда в изучении уже столько слов, сколько
   разрешает лимит: повторения при этом продолжают приходить.
5. В один слот уходит одно **основное** слово (это и есть дневной лимит) и,
   при наличии, одно слово **на освежение** — отдельным сообщением, лимит оно
   не расходует.
6. Основное слово выбирается по ступеням: повторения, которых сегодня ещё не
   было, → новое слово → повторение того, что уже показывали сегодня
   (`services/word_selector.py`, `select_main_word`).
7. **Никаких напоминаний**, если пользователь не ответил: следующее слово
   придёт по расписанию.
8. Пропущенные слоты не «догоняются» задним числом (`misfire_grace_time`),
   после перезапуска расписания восстанавливаются из БД.

## Система повторений (SRS)

| Этап | Интервал до следующего показа | «Знаю» | «Не знаю» |
|------|------------------------------|--------|-----------|
| 0 | в тот же день | этап 1 | этап 0 |
| 1 | 1 день | этап 2 | этап 0 |
| 2 | 3 дня | этап 3 | этап 0 |
| 3 | 7 дней | этап 4 | этап 0 |
| 4 | 14 дней | этап 5 | этап 0 |
| 5 | 30 дней | этап 6 → `learned` | этап 0 |
| 6 | 90 дней (освежение) | остаётся `learned` | этап 0 (`learning`) |

- **Порядок очереди основного слова** (`services/word_selector.py`): сначала
  повторения, которых **сегодня ещё не показывали** (самые просроченные вперёд;
  ``not_shown_since`` = начало местных суток пользователя), затем новое слово, и
  только потом — повторение слова, которое сегодня уже приходило. Без такого
  порядка «Не знаю» (этап 0, срок наступает сразу) зацикливал очередь на одних и
  тех же словах, а новые не приходили.
- Новые слова выбираются случайно (`ORDER BY random()`), сначала из тех, что ещё
  ни разу не приходили; проигнорированное слово может вернуться позже.
- Новые слова не приходят, пока слов «в изучении» (этапы 0–5) не меньше
  `users.learning_limit`; `0` в настройках снимает ограничение. Повторения уже
  начатых слов и освежение лимит не ограничивает.
- Выученные слова (`learned`) приходят только в очередь освежения; ошибка на
  освежении возвращает слово в изучаемые.
- Ответ фиксируется в `delivery_log`, после ответа инлайн-кнопки у сообщения
  убираются — повторный клик статистику не меняет.
- «Сегодня» считается по часовому поясу пользователя
  (`services/slots.local_day_start_utc`): для `Europe/Moscow` сутки начинаются в
  21:00 UTC предыдущего дня. Слово, показанное сегодня, второй раз в тот же день
  не приходит, пока есть другие варианты.

## Формат сообщения

Режим «сначала слово, потом перевод»: сообщение содержит только слово и кнопку
**Показать**; после нажатия приходит полная карточка с кнопками
**Знаю / Не знаю** и **🔊 🇬🇧 UK / 🔊 🇺🇸 US** (озвучка приходит отдельным
сообщением, см. [озвучку слов](#озвучка-слов)).

Режим «всё сразу»: перевод под спойлером Telegram, остальные поля — отдельными
строками (по умолчанию: определение, пример, коллокации, синонимы, антонимы;
часть речи и однокоренные включаются в `/settings`):

```
apple - ||яблоко||

📖 a round fruit with red or green skin
✍️ She ate an apple for breakfast.
🔗 green apple
🟰 fruit
↔️ vegetable
```

Подписи полей: 📖 Definition, ✍️ Example Sentence, 🏷 Part of Speech,
🧬 Related Forms, 🟰 Synonyms, ↔️ Antonyms, 🔗 Collocations. Выключенные поля в
сообщение не попадают; пустые значения скрываются, а для коллокаций, синонимов и
антонимов вместо пустого значения выводится прочерк `—`. Весь текст экранируется
для `MarkdownV2`.

Сообщение со словом на освежение содержит ту же карточку плюс подсказку
«🔁 Освежение: этот повтор не входит в дневной лимит.», а после ответа к тексту
добавляется результат («правильно», «слово вернётся» и т.п.).

## Схема базы данных

SQLite, пять таблиц (создаются автоматически):

| Таблица | Назначение | Ключевые поля |
|---------|------------|---------------|
| `words` | словарные статьи | `word` (уникальный), `definition`, `russian_translation`, `example`, `part_of_speech`, `related_forms`, `synonyms`, `antonyms`, `collocations` |
| `users` | пользователь и его настройки рассылки | `telegram_id` (уникальный), `timezone`, `words_per_day`, `learning_limit`, `window_start`, `window_end`, `reveal_mode`, `pos_filter` (JSON-список), `paused`, `created_at` |
| `user_settings` | какие поля показывать в карточке | `user_id`, `show_definition`, `show_example`, `show_pos`, `show_related`, `show_synonyms`, `show_antonyms`, `show_collocations` |
| `user_words` | прогресс SRS по слову | `user_id`, `word_id` (уникальная пара), `stage`, `status`, `next_review_at`, `last_reviewed_at`, `times_correct`, `times_wrong`, `is_refresh` |
| `delivery_log` | журнал отправок и ответов | `user_id`, `word_id`, `sent_at`, `answered_at`, `answer` |

Все временные метки — UTC. `fetch_due_user_words` (SQLAlchemy/aiosqlite) выбирает
очередь: слова к повторению по `next_review_at` (сначала те, что дольше ждали
показа, — `last_reviewed_at`), `fetch_new_words` — новые слова в случайном порядке,
`fetch_refresh_user_words` — освежение выученных. Параметр `not_shown_since`
(начало местных суток из `services/slots.local_day_start_utc`) отсекает слова,
которые пользователю уже показывали сегодня.

Схему бот обновляет сам: `Base.metadata.create_all` дополняется мини-миграциями
(`db/migrations.py`, `PRAGMA table_info` + `ALTER TABLE`), поэтому существующий
`bot.db` не нужно удалять, когда в таблицах появляются новые колонки.

## Частые вопросы и проблемы

**Бот молчит на все команды, а в `logs\bot.log` пусто.**
Так выглядит рассинхрон фильтров команд: aiogram сравнивает с названием команды
**без** префикса, поэтому `Command("/start")` (со слэшем, как команды хранятся в
`locales/ru.py`) не совпадает ни с чем. Для фильтров используйте
`common.command_filter(texts.CMD_START)` — он сам убирает `/`. Теперь такие
ситуации видно в логах: сообщение без обработчика пишется предупреждением
(`handlers/common.py`, роутер `fallback`), а внутренние логи aiogram идут в
`bot.log` вместе с основными (`logging_setup.InterceptHandler`).

**Бот совсем не реагирует на команды (`TelegramConflictError` в логах).**
Запущено несколько экземпляров бота с одним токеном — они отбирают друг у друга
`getUpdates`. Оставьте один процесс:

```powershell
Get-Process python | Select-Object Id, CommandLine   # найти лишние
Stop-Process -Id <Id>                                # оставить один
```

Проверить, кто реально держит polling: параллельный запрос
`https://api.telegram.org/bot<TOKEN>/getUpdates` вернёт `409 Conflict`, если бот
работает, и обычный JSON — если ни один процесс апдейты не забирает.

```bash
systemctl status tele-eng-bot     # Linux: этот сервис должен быть единственным
pgrep -af main.py                 # лишние процессы бота на сервере
```

Если бот запущен и локально, и на сервере с одним токеном, оставьте один
экземпляр: `sudo systemctl stop tele-eng-bot` на сервере либо остановка локального
процесса. На сервере сервис тоже должен быть один — не запускайте
`python main.py` руками параллельно с юнитом `systemd`.

Второй экземпляр заметен и по алертам «⚠️ Не нашёл это слово в истории отправок»:
нажатие достаётся процессу со своей базой, и он не знает чужих карточек. Какую
базу держит процесс, видно по файлу: `sudo lsof -p <pid> | grep bot.db`
(на Windows — `Get-Process python | Select-Object Id` плюс путь из `.env`).
Подробнее — в следующем пункте.

**Бот запустился, но слова не приходят.**
Проверьте `/settings`: окно рассылки, число слов и часовой пояс; слоты идут по
местному времени пользователя. Слова не отправляются вне окна, на паузе
(`/pause`) и если очередь пуста (в конце списка ждите освежений).

**Не работает кнопка «✍️ Ввести вручную» (окно, число слов, часовой пояс).**
Кнопка должна нести **действие шага** и значение `manual`
(`settings:window:manual`, `reg:words:manual`), иначе её не совпадает ни один
фильтр хендлера. Формируется она в `keyboards/inline.py`
(`_with_tail(..., manual_action=config.ACTION_WINDOW)`), а забытые кнопки теперь
видны в логе: «Кнопка без обработчика» (`handlers/common.py`, роутер `fallback`).
После нажатия бот спрашивает время в формате `ЧЧ:ММ`: сначала начало окна, потом
конец; для отмены — `/cancel`.

**`/word` и «🎲 Слово» присылают одно и то же слово.**
Так было, когда ручной запрос брал самое «просроченное» слово из очереди: у него
срок повторения наступил и остаётся наступившим до ответа, а после «Не знаю» он
обнуляется (этап 0). Теперь ручной запрос исключает карточки без ответа за
**сегодня** и слово из последней отправки (`services/word_selector.py`,
`on_demand_exclusions`), а очередь сначала отдаёт повторения, которых сегодня ещё
не было, затем новое слово — поэтому подряд приходят разные слова. Повтор
возможен, только когда других слов не осталось — тогда в `bot.log` появляется
строка «других слов нет — повторяю слово из очереди». Висящая карточка прошлых
суток слово больше не исключает: раньше из-за неё слово навсегда выпадало из
ручного запроса, пока на ту карточку не ответят.

**Бот присылает одни и те же слова и не даёт новых.**
Причина была в порядке очереди: слова с наступившим сроком повторения (этап 0
после «Не знаю») выбирались **всегда раньше** новых слов, поэтому свежие слова из
словаря не приходили вообще. Теперь `services/word_selector.py`
(`select_main_word`) идёт по трём ступеням: (1) повторения, которых сегодня ещё
не было, (2) новое слово, (3) повторение того, что уже показывали сегодня.
Слово, показанное сегодня, возвращается только в третьем случае — например, когда
достигнут лимит слов в изучении или в словаре не осталось новых слов по фильтру
части речи.

**Новые слова перестали приходить.**
Скорее всего, достигнут лимит слов в изучении (`/settings` → «📚 Лимит в
изучении»): пока слов «в изучении» (этапы 0–5) не меньше лимита, новые слова не
показываются — ни по расписанию, ни по кнопке «🎲 Слово»
(`services/word_selector.py`, `new_words_allowed`). По команде `/word` бот в этом
случае прямо пишет «Лимит слов в изучении: N из M». Повторения уже начатых слов
продолжают приходить: отвечайте на них (слова выходят из изучения) или поднимите
лимит — либо поставьте `0`/«♾ Без ограничения».

**Новые слова идут в произвольном порядке — так и задумано.**
Очередное новое слово выбирается случайно (`ORDER BY random()` в
`db/repository.py`, `fetch_new_words`), приоритет — у слов, которых у
пользователя ещё не было. Раньше слова шли подряд по алфавиту словаря.

**После обновления кода падает `no such column: users.learning_limit`.**
Удалять базу не нужно: недостающие колонки бот дописывает при старте
(`db/migrations.py` → `database.init_database`, в логе — «Схема БД обновлена,
добавлены колонки»). Если ошибка всё же появилась, проверьте, что запускается
актуальный код из корня проекта (`.\\.venv\\Scripts\\python.exe main.py`).

**`Ошибка: не задан BOT_TOKEN`.**
Скопируйте `.env.example` в `.env` и укажите токен от @BotFather.

**`ZoneInfoNotFoundError` при запуске на Windows.**
В `zoneinfo` нет системной базы часовых поясов, нужен пакет `tzdata` (он уже
указан в `requirements.txt`): выполните `pip install -r requirements.txt`.

**В базе нет слов / `Файл словаря не найден`.**
Проверьте `CSV_PATH` и наличие файла, затем выполните
`python scripts/import_csv.py`.

**Хочу начать заново.**
Остановите бота и удалите `bot.db` (при следующем запуске схема и словарь
создадутся заново). Файлы `bot.db-wal`/`bot.db-shm` тоже можно удалить. Старые
сообщения со словами после этого перестанут работать: кнопки в них ссылаются на
журнал отправок прежней базы (см. ниже).

**Кнопка отвечает «⚠️ Не нашёл это слово в истории отправок».**
Так бот реагирует, когда `callback_data` кнопки ссылается на запись, которой нет
в `delivery_log` (`handlers/word_actions.py`, `_fetch_delivery`). Строки журнала
нигде не удаляются, поэтому при обычной работе (в том числе после перезапуска
бота или сервера — журнал лежит в базе, а не в памяти) такого не бывает:
причина внешняя.

- **База пересоздана.** Удалён `bot.db` («Хочу начать заново») или бот развёрнут
  на новом сервере с чистой базой — старые сообщения в чате несут прежние
  идентификаторы отправок. Лечится новым словом: `/word` или «🎲 Слово».
- **База перенесена без журнала WAL.** Скопирован только `bot.db`, а свежие
  отправки лежали в `bot.db-wal` — при переносе они потерялись. Копируйте базу
  целиком или через `VACUUM INTO` (см. «Бэкап, перенос базы и удаление сервиса»).
- **Работает другой экземпляр бота.** Два процесса с одним токеном (например,
  локальный и серверный) отбирают друг у друга `getUpdates`, и нажатие достаётся
  тому, у кого своя база — карточек из неё он не знает. В логе это видно вместе
  с `TelegramConflictError` (см. ниже), а заодно с предупреждением о размере
  журнала: `delivery_id` больше максимального id, то есть база заведомо не та.
- **Кнопку нажал чужой аккаунт.** Инлайн-кнопки пересылаются вместе с сообщением,
  поэтому карточку может открыть пользователь, которому отправка не принадлежит.

Причина каждого случая пишется в `logs/bot.log` предупреждением: «Кнопка без
отправки», «Кнопка от чужой отправки» или «Кнопка от другого слова» — с номерами
`delivery_id`, `user_id` и слова. В строке «Кнопка без отправки» есть ещё число
записей журнала, максимальный id и путь к базе:

```
Кнопка без отправки: delivery_id=72 нет в delivery_log (пользователь 1375937821,
слово 1951). В журнале 12 записей, максимальный id=12
(база /opt/tele_eng/bot.db). База пересоздана или перенесена без WAL?
```

`delivery_id=72` при `максимальный id=12` — однозначный признак, что эта база
карточку не отправляла: сверьте путь с рабочим каталогом бота (`DB_PATH` в `.env`,
по умолчанию `bot.db` рядом с кодом) и проверьте, не запущен ли где-то второй
экземпляр. Пользователю приходит только общий алерт.

**Ответил на слово, но хочу вернуть его в оборот.**
Нажмите «Не знаю» — слово вернётся на нулевой этап и придёт снова; выученные
слова и без этого возвращаются на освежение раз в 90 дней.

**Бот тормозит на персональном сервере.**
Уменьшите `words_per_day`, сократите окно или поставьте паузу. Импорт словаря
идёт один раз, дальше бот читает только SQLite.
